= LangChain4j Agentic Viewer
:extension-status: experimental

include::./includes/attributes.adoc[opts=optional]

The Agentic Viewer adds an *Agentic Systems* page to the Quarkus Dev UI. It shows the LangChain4j agentic systems of
your application as interactive graphs (structure and data flow), and runs them with live highlighting, a timeline of
every agent and tool call, the AgenticScope state, and dedicated views for supervisors, planners and the patterns of
`langchain4j-agentic-patterns`.

It only exists in dev mode: nothing of it is part of a production or native build.

== Installation

Add the extension next to `quarkus-langchain4j-agentic`:

[source,xml,subs=attributes+]
----
<dependency>
    <groupId>io.quarkiverse.langchain4j</groupId>
    <artifactId>quarkus-langchain4j-agentic-viewer</artifactId>
    <version>{project-version}</version>
</dependency>
----

Start the application in dev mode (`mvn quarkus:dev`), open the Dev UI (`http://localhost:8080/q/dev-ui`) and click
*Agentic Systems* on the *LangChain4j Agentic Viewer* card.

== The systems of your application

Every root agentic system declared with the agentic annotations (`@SequenceAgent`, `@ParallelAgent`,
`@ParallelMapperAgent`, `@LoopAgent`, `@ConditionalAgent`, `@SupervisorAgent`, `@PlannerAgent`, `@Agent`,
`@HumanInTheLoop`, `@A2AClientAgent`, `@McpClientAgent`...) is found at build time: a root is an agent that no other
agent lists as a sub-agent. The page lists them with the patterns they use.

image::list.png[The list of agentic systems]

=== Systems built with the builders

Systems built with `AgenticServices.*Builder()` only exist at runtime. The page also lists those the application
produces as CDI beans: a producer whose type is an agent (`UntypedAgent`, `SupervisorAgent`), or whose body calls a
builder's `build()` (a typed agent interface):

[source,java]
----
@Produces
@ApplicationScoped
@Named("storyCreator")
UntypedAgent storyCreator(ChatModel chatModel) {
    return AgenticServices.sequenceBuilder()
            .subAgents(AgenticServices.agentBuilder(Drafter.class).chatModel(chatModel).build(), ...)
            .outputKey("story")
            .build();
}
----

Their beans are created when the page first lists the systems, not at startup. A produced system used as a sub-agent of
another one is shown inside it, not as a system of its own. Their graph is read from the live agents: a loop exit
condition or an activation condition given as a lambda without description is shown as "lambda", and tools or models
given to a builder directly are not shown. `quarkus.langchain4j.agentic.dev-ui.builder-discovery=none` lists the
declarative systems only.

Systems that are not beans (kept in a field, built per request) are found with
`quarkus.langchain4j.agentic.dev-ui.builder-discovery=transform`: in dev mode only, the application classes calling a
builder's `build()` are rewritten to report what they build. Such a system appears once it has been built (after the
first request, for one built per request), once per place in the code (its latest instance), named after the
`name(...)` given to the builder.

A builder system using agents that a declarative system of the application also uses is shown as _mixed_ (those
agents show their build-time details), as is a declarative system whose agent injects a builder system.

They run from the page like the others, with the same live view (agents, timeline, human steps, planner decisions).
The form asks for the inputs their agents need from the caller (the parameters of the method, for a typed agent
interface): an `UntypedAgent` is invoked with a map of these values.

TIP: Give each builder system its own agents (`AgenticServices.agentBuilder(MyAgent.class).chatModel(...)`), not the
agent beans Quarkus creates for the agent interfaces: a langchain4j agent has one parent, and a declarative system using
the same bean would then be broken.

=== Structure

The structure view draws each workflow as a box containing its sub-agents, in declaration order: arrows for a
sequence, a fork and a join for parallel branches (with the activation condition of each branch of a conditional), a
back edge with the exit condition for a loop, and dashed candidates for a supervisor or a planner, whose sub-agents
are only chosen at run time.

image::structure.png[The structure of a system with a loop]

=== Data flow

The data-flow view links the agents by the AgenticScope keys they share: an edge from the agent writing a key (its
`outputKey`) to every agent reading it (its `@V` parameters), and the inputs of the system on top.

image::dataflow.png[The data flow of a supervisor]

=== Wiring warnings

Before any run, the page checks the wiring of each system and lists what it finds above the graph; the nodes concerned
carry a badge (⚠ warning, ⓘ hint) and show it in their details:

* warning: a `@ConditionalAgent` sub-agent without `@ActivationCondition` (langchain4j leaves it out, it never runs);
* warning: a loop without exit condition and more iterations than `quarkus.langchain4j.agentic.dev-ui.loop-warning-iterations`
  (5 by default): it always runs them all;
* hint: an output key nothing in the system reads (agents, conditions, `@Output`);
* hint: a key an agent reads that no agent of the system writes and that is no input of the system.

Hints are left out under supervisors, planners and parallel mappers, whose agents get their arguments at runtime, and
the second one in systems with a non-AI agent without output key (it may write the scope in code). quarkus-langchain4j
already rejects keys no agent of the whole application writes; these checks look at one system. Builder systems are
checked the same way (what their lambdas read is unknown: no "never read" hint for them).

=== Details

Clicking a node opens its details: description, input and output keys, flags, the exit or activation condition, and
for an AI agent its system and user messages, model (its `@ModelName`, or the `@ChatModelSupplier` or
`@StreamingChatModelSupplier` method giving it), skills (`@Skills`) and tools. Settings that change how an agent
behaves are shown when set: `compensateOnError` (compensation of the earlier tool calls when a tool fails), the agents
of its `summarizedContext`, and for a supervisor its maximum of invocations, context strategy and response strategy,
marked when they are the defaults. For a system built with the builders, they come from the annotations of its agent
types: the settings of the workflows the builders make are not known.

The *Code* section lists the application code behind the node: the agent method, a workflow's `@Output`, a planner's
`@PlannerSupplier`, the exit and activation conditions, the prompt resources (`fromResource`), the tools, the methods
configuring the agent (chat model, chat memory, content retriever, retrieval augmentor, message provider and agent
listener suppliers, `@BeforeCall`), and where a builder system is built. Code found in the application sources shows
its file and line; when the Dev UI detected your IDE, a click opens it there. Code of dependencies is listed without a
link.

== Running a system

The *Run* button opens a form generated from the parameters of the root method (text, numbers, booleans, enums, and
JSON for anything else), then runs the system in the application, exactly as your code would.

[IMPORTANT]
====
A run executes the system for real: its models are called, and its tools run with their side effects and cost.
Before the first run of a system in a browser session, the Dev UI lists every tool the system can reach (`@Tool`
methods, tool providers, MCP tools, remote A2A agents) and asks for a confirmation.

In dev, prefer a model that costs nothing and changes nothing: a local model, or a fake one. For example, any
OpenAI-compatible local server, such as Ollama, works with `quarkus-langchain4j-openai`:

[source,properties]
----
%dev.quarkus.langchain4j.openai.base-url=http://localhost:11434/v1
%dev.quarkus.langchain4j.openai.api-key=ollama
%dev.quarkus.langchain4j.openai.chat-model.model-name=qwen2.5:14b
----

The viewer never chooses a model: each agent uses the model your application configures for it. Tests and samples
can also provide their own `ChatModel` bean answering scripted replies.
====

image::tools-confirmation.png[The confirmation listing the tools a run can reach]

=== Live view

While the run executes, the graph highlights the agents as they start and finish, with their duration and token
usage, the iterations of loops and the items of parallel mappers. The timeline below the graph shows every
invocation, nested by its parent, with the tool calls (click one for its arguments and result); the *Scope* tab shows
the AgenticScope keys as agents write them.

image::live.png[A supervisor run with its timeline]

A supervisor shows the path it took: the sub-agents it called are linked by solid, numbered edges over the dashed
candidates. A planner (a `@PlannerAgent` with its own `@PlannerSupplier`) is shown step by step: each decision is a
numbered step on the graph and a row of the timeline.

A `@HumanInTheLoop` step pauses the run: the Dev UI shows what the step asks and its inputs, and the answer you type
resumes the run (the annotated method is not called in a run started from the Dev UI; anywhere else it is).

image::human-in-the-loop.png[A run waiting for a human answer]

Errors show the failing agent and the exception; an `@ErrorHandler` that retried or recovered is shown on the node and
in the timeline. Past runs stay in the *Recent runs* list (20 per system by default) and can be replayed on the graph,
also after a page reload.

=== Comparing two runs

Tick two runs in *Recent runs* and click *Compare*: the *Compare* tab shows their inputs, totals (status, duration,
tokens) and every agent invocation matched across them (same node, loop iteration and mapper item, under the same
parents), with both outputs and what changed. Invocations only one run made (another loop count, another conditional
branch, another supervisor path) are listed as such, and the graph is colored: same, changed, run by one run only.
Values cut by the payload limit (`max-payload-size`) that agree up to the cut show as possibly different. Runs are kept
by the application: a hot reload starts a new history.

*Re-run after a reload* (off by default, per system) runs the last inputs again each time the application reloads
(a reload happens on the next request after a code change, e.g. a browser refresh), and compares the new run with the
one before the reload, kept in the page. It does not run when the system is gone, its inputs changed, or its tools
were never confirmed by a run of yours: each run calls the real models and tools.

== Pattern views

When `dev.langchain4j:langchain4j-agentic-patterns` is on the class path (there is no Quarkus extension for it: add it
directly), the planners it provides get dedicated views. Without it, nothing of these views is loaded. Their nodes are
tagged with the pattern instead of "Planner" (graph, node details, timeline, system list).

Goal-oriented planner (GOAP):: The planner node shows the dependency graph of its agents by keys, with the goal key.
The run form previews the path the planner will take for the inputs entered, using the planner's own search; during
the run the path is highlighted, then walked step by step.
+
image::goap.png[A goal-oriented planner with its path preview]

Peer-to-peer:: The planner node shows its agents and the state keys they read and write (cycles included). During the
run, keys light up as they are written, agents as they can activate, an invocation counter runs against the maximum,
and the end tells why the planner stopped: exit condition, maximum invocations or stable state.
+
image::p2p.png[A peer-to-peer run that stopped on its exit condition]

Blackboard:: The agents are drawn around the blackboard (the scope). Each step shows the candidates that could fire,
the one the conflict resolution strategy picked, and the goal status; the end tells whether the goal was reached or
no agent could fire.
+
image::blackboard.png[A blackboard run]

BDI (belief-desire-intention):: The planner node shows its desires, highest priority first, each linked to the agents
it calls in order; the node details tell when each desire is achievable and satisfied. Each step of a run tells the
desire it pursues, and the end how many desires are satisfied. The desires are read from the `@PlannerSupplier` when it
declares them with literals (`Desire.of("name", 10, "achievableKey", "satisfiedKey", Agent.class)`, or predicates,
whose conditions then show as custom); desires built elsewhere, and those of a builder system (the planner keeps them
private), are not shown.

Debate:: The debaters (every sub-agent but the last) are drawn side by side with a back-edge for the next round, and
the judge (the last sub-agent) after them. Each step of a run tells the round, and when the judge is called. Why the
judge was called (the debaters agreed, or the last round was reached) is not told: the maximum of rounds and the
convergence strategy are private to the planner.

Voting:: The voters are drawn side by side, their outputs going into the tally. The end of a run tells each vote and
the result; the voting strategy is private to the planner and not told.

== Describing a custom planner

A custom planner's structure is in its code: by default the viewer draws its sub-agents as candidates. To draw what it
does, implement `AgenticTopologyContributor` (an interface of the extension's runtime artifact) with a public
no-argument constructor; it is found at build time and only called in dev mode:

[source,java]
----
public class DraftReviewTopology implements AgenticTopologyContributor {

    @Override
    public Class<?> plannerAgent() {
        return DraftReviewer.class; // the @PlannerAgent interface declaring the @PlannerSupplier
    }

    @Override
    public TopologyContribution contribute(AgentNode plannerNode) {
        return new TopologyContribution(
                List.of(new ContributedNode("done", "approved or 3 drafts")),
                List.of(new ContributedEdge("writeDraft", "review", "draft"),
                        new ContributedEdge("review", "writeDraft", "rejected"),
                        new ContributedEdge("review", "done", "approved")));
    }
}
----

Edges name sub-agents by agent name (or node id) and contributed nodes by id. The contribution replaces the
candidates of that planner node; during a run, the step numbers go on the nodes.

image::contributor.png[A custom planner drawn by its topology contributor]

== Limitations

* Builder systems are listed when they are CDI beans; systems kept in a field or built per call only with
  `builder-discovery=transform`, once built.
* Runs, human-in-the-loop answers, planner decisions and the pattern views rely on internal parts of
  `langchain4j-agentic` and `langchain4j-agentic-patterns` (there is no public API for them yet). A version of these
  libraries that changes them may disable some of the live information; the structure views do not depend on them.
* Everything is dev mode only: `quarkus.langchain4j.agentic.dev-ui.enabled=false` also turns it off in dev mode.
